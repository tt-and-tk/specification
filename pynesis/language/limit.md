# 量的制限
プログラムの大きさには次の上限がある．上限を超えるとコンパイルエラーになるものと，コンパイラが検査せず実行時に誤った動作になるものがある．  

| 制限 | 上限 | 超えた場合 |
|:-|:-|:-|
| 命令数 | ROM用は16384命令．実行ファイル用は，グローバル変数とスタックの量で決まる(「命令数」を参照) | コンパイルエラー |
| 変数に使えるメモリ | 出力先によって異なる(「変数に使えるメモリ」を参照) | 検査できる範囲でコンパイルエラー |
| 関数呼び出しの深さ | 固定の上限はなく，スタックに使える量で決まる(ROM用はカーネル用の範囲の残り，実行ファイル用は割り振られたスタックの量) | 検査できる範囲でコンパイルエラー |
| 式の複雑さ | 汎用レジスタ16本(r0〜r15)で評価できる範囲 | コンパイルエラー |

# 命令数
命令数の上限は，出力先によって次のとおり決まる．  

- ROM用: ROMの容量で決まる([qurge/rom.md](../../qurge/rom.md)の「容量と命令数の上限」を参照)  
- 実行ファイル用: 命令列・グローバル変数・スタックの合計が，置ける範囲に収まる必要がある(「変数に使えるメモリ」を参照)．このため上限は，グローバル変数とスタックを置くほど少なくなる．最も多い場合は，グローバル変数が無く，スタックの量が`main`の終了で使う24バイトの場合の12253命令である  

# 変数に使えるメモリ
グローバル変数とスタックを置ける範囲は，出力先によって異なる．次の図は，出力先ごとのメモリ上の配置を，番地の大きい側を上にして示す．  

```
ROM用(メモリの番地)

0x8000 +-------+ <- SPの初期値
       |   |   |    スタック(下へ伸びる)
       |   v   |
       |       |    空き
       |   ^   |
       |   |   |    グローバル変数(上へ伸びる)
0x0000 +-------+
```

```
実行ファイル用(領域の中の番地．Sは領域の大きさ)

     S +-------+
       |       |    引数の置き場(コマンド名と引数)
       |-------| <- SPの初期値(Qosmosが引数の置き場の中に決める)
       |   |   |    スタック(下へ伸びる)
 S-256 +---|---+
       |   v   |
       |-------| <- スタックの量の下端
       |       |    グローバル変数
       +-------+
       |       |    命令列
0x0000 +-------+
```

出力先ごとの範囲は，次のとおりである．  

- ROM用: グローバル変数とスタックの合計が，カーネル用の範囲(`0x00000`〜`0x07FFF`の32768バイト)に収まる必要がある([qurge/cpu/mode.md](../../qurge/cpu/mode.md)の「メモリを読み書きできる範囲」を参照)  
- 実行ファイル用: 命令列・グローバル変数・スタックの量の見積もりの合計が，98048バイト以下である必要がある．スタックの量を見積もれない場合は，4096バイトをスタックの量とする(「スタックの量を見積もれない場合」を参照)．Qosmosは，この合計に合わせた大きさの領域を割り振る．98048バイトと領域の大きさの決め方は，[qosmos/kernel/memory.md](../../qosmos/kernel/memory.md)の「領域の大きさ」を参照  

## コンパイルエラーになる場合
次の場合は，コンパイルエラーになる．  

- グローバル変数だけで，置ける範囲(ROM用はカーネル用の範囲の32768バイト，実行ファイル用は98048バイト)を超える場合  
- ROM用で，スタックの量を見積もれるプログラムのグローバル変数とスタックの合計が，カーネル用の範囲を超える場合  
- 実行ファイル用で，命令列(1命令8バイト)・グローバル変数・スタックの量の合計が，98048バイトを超える場合(スタックの量を見積もれない場合は4096バイトとして合計する)  

スタックの量は，呼び出しの経路から見積もる．関数ポインタを通した呼び出しは，番地を取得された関数のうち型が一致するものを，すべて呼び出し先として見積もる．見積もり方と，見積もりに含めない呼び出し先は，[pynesis/compiler/check.md](../compiler/check.md)の「スタックの量の見積もり」を参照．  

## スタックの量を見積もれない場合
次の場合は，コンパイラがスタックの量を見積もれない．  

- 再帰呼び出しがある場合: スタックの深さが実行時にしか決まらないため  
- 関数ポインタを通した呼び出しやasm文の入力に書いた関数を含めてたどると，呼び出しが循環する場合: 再帰呼び出しと同じ理由である．番地を取得された関数のうち型が一致するものと，asm文の入力に書いた関数をすべて呼び出し先とみなすため，実際には起きない循環もこれに当たる([pynesis/language/asm.md](asm.md)の「関数名」を参照)  
- 実行ファイル用で，asm文か，整数と関数ポインタの間でキャストする式を含む場合: 見積もりに含められない呼び出し先を持ちうるため([pynesis/compiler/check.md](../compiler/check.md)の「見積もらない場合」を参照)  

見積もれない場合は，出力先によって次のように検査する．  

- ROM用: スタックを含めずに，グローバル変数の大きさだけを検査する  
- 実行ファイル用: 4096バイトをスタックの量として検査する．実行時に使えるスタックは，Qosmosが割り振る4096バイトまでである([qosmos/kernel/memory.md](../../qosmos/kernel/memory.md)の「領域の大きさ」を参照)  

どちらの場合も，実際に使うスタックが変数と重なっても，コンパイラとCPUは検出しない([qurge/cpu/stack.md](../../qurge/cpu/stack.md)の「深さの上限」を参照)．  

# 式の複雑さ
1つの式は，汎用レジスタ16本(r0〜r15)で評価できる範囲に収める必要がある．コンパイラが式ごとに検査し，超えるとコンパイルエラーになる．評価の途中の値を，足りなくなった分だけメモリへ逃がして評価を続けることはしない．  

入れ子が深い式ほど，多くのレジスタを同時に使う．入れ子が浅くても，組み込み関数のように評価に多くの作業用の値を使う構文を含むと，上限に達しうる．
